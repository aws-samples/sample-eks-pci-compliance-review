# Pillar: Scheduling & Node Isolation (SI1-SI5)

Focus: Node isolation and workload scheduling controls to ensure CDE workloads run on dedicated, appropriately configured nodes separated from non-CDE workloads. Grade each check PASS / FAIL / N/A with evidence, severity, and PCI DSS requirement mapping.

PCI DSS anchor: Requirement 2.2.3 (primary functions with different security levels on separate systems), Requirement 2.2.6 (system security parameters configured to prevent misuse).

Reference: [Building PCI DSS-Compliant Architectures on Amazon EKS — §3 Multi-Tenant Scheduling & Node Isolation](https://aws.amazon.com/blogs/containers/building-pci-dss-compliant-architectures-on-amazon-eks/)

| Check ID | Check Name | CDE Scope | Data Source | What to Look For | Severity if Failed | PCI DSS Req | Recommendation |
|----------|------------|-----------|-------------|------------------|-------------------|-------------|----------------|
| SI1 | CDE node taints configured | Cluster | `kubectl get nodes -o json` (spec.taints) | Nodes designated for CDE workloads have taints that prevent non-CDE pods from scheduling (e.g., `pci-scope=cde:NoSchedule`) | High | 2.2.3 | Configure taints on CDE-designated nodes (e.g., `pci-scope=cde:NoSchedule`) to restrict pod scheduling to specifically tainted nodes. This supports PCI DSS Req 2.2.3 by separating functions with different security levels. See: https://kubernetes.io/docs/concepts/scheduling-eviction/taint-and-toleration/ |
| SI2 | CDE pods have matching tolerations | CDE-only | `kubectl get pods -n {cde} -o json` (spec.tolerations) | Pods in CDE namespaces have tolerations matching the CDE node taints, confirming they are scheduled on dedicated CDE nodes | Medium | 2.2.3 | Add tolerations to CDE workloads matching the CDE node taints. This ensures CDE pods are scheduled on the dedicated CDE nodes. Example: `tolerations: [{key: "pci-scope", operator: "Equal", value: "cde", effect: "NoSchedule"}]`. Supports PCI DSS Req 2.2.3. |
| SI3 | Node affinity/nodeSelector for CDE workloads | CDE-only | `kubectl get pods -n {cde} -o json` (spec.nodeSelector or spec.affinity.nodeAffinity) | CDE pods use nodeSelector or nodeAffinity to target CDE-labeled nodes (e.g., `node-role=pci-cde`) | High | 2.2.6 | Implement `nodeSelector` or `nodeAffinity` rules on CDE workloads to ensure they deploy only to appropriately labeled CDE nodes. Example: `nodeSelector: { node-role: pci-cde }`. Supports PCI DSS Req 2.2.6. See: https://kubernetes.io/docs/concepts/scheduling-eviction/assign-pod-node/ |
| SI4 | Dedicated node groups for CDE | Cluster | `kubectl get nodes --show-labels` | Distinct node group(s) exist for CDE workloads, identifiable by labels (e.g., `node-group=pci-cde` or separate Karpenter NodePool/EC2NodeClass) | High | 2.2.6 | Create dedicated node groups (managed nodegroups, Karpenter NodePools, or Auto Scaling Groups) for CDE workloads. Separate node groups provide hardware-level isolation boundary. Supports PCI DSS Req 2.2.6. See: https://docs.aws.amazon.com/eks/latest/userguide/managed-node-groups.html |
| SI5 | Inter-pod anti-affinity for CDE tenant isolation | CDE-only | `kubectl get pods -n {cde} -o json` (spec.affinity.podAntiAffinity) | CDE workloads use hard anti-affinity constraints (`requiredDuringSchedulingIgnoredDuringExecution`) to prevent co-scheduling of different tenant workloads on the same node | Medium | 2.2.3 | Implement `podAntiAffinity` with `requiredDuringSchedulingIgnoredDuringExecution` to prevent pods from different tenants or services from being co-scheduled on the same node. This reduces blast radius of a compromised container. Supports PCI DSS Req 2.2.3. See: https://kubernetes.io/docs/concepts/scheduling-eviction/assign-pod-node/#inter-pod-affinity-and-anti-affinity |
