# Pillar: Namespace Isolation (NS1-NS9)

Focus: Logical separation of workloads within the EKS cluster to support segmentation of Cardholder Data Environments (CDE) from non-CDE workloads. Grade each check PASS / FAIL / N/A with evidence, severity, and PCI DSS requirement mapping.

PCI DSS anchor: Requirement 1.3.2 (restrict pod traffic), Requirement 1.4.1/1.4.2/1.4.4 (guardrails on authorized traffic), Requirement 2.2.1 (resource limits), Requirement 7.2.5 (least privilege access).

Reference: [Building PCI DSS-Compliant Architectures on Amazon EKS — §1 Namespace Isolation](https://aws.amazon.com/blogs/containers/building-pci-dss-compliant-architectures-on-amazon-eks/)

| Check ID | Check Name | CDE Scope | Data Source | What to Look For | Severity if Failed | PCI DSS Req | Recommendation |
|----------|------------|-----------|-------------|------------------|-------------------|-------------|----------------|
| NS1 | Dedicated namespaces per application | All | `kubectl get namespaces` | Each application or tenant has its own namespace; no shared "default" namespace usage for workloads | Medium | 1.4.1 | Create dedicated namespaces per application or tenant. Do not deploy workloads in the `default` namespace. This supports PCI DSS Req 1.4.1 by establishing logical boundaries for traffic control. See: https://docs.aws.amazon.com/eks/latest/best-practices/security.html |
| NS2 | RBAC roles namespace-scoped in CDE | CDE-only | `kubectl get rolebindings -n {cde}` + `kubectl get clusterrolebindings` | CDE namespaces use namespace-scoped RoleBindings rather than ClusterRoleBindings for access; no ClusterRoleBindings grant broad access to CDE namespaces | High | 7.2.5 | Use namespace-scoped Roles and RoleBindings for CDE namespaces. Avoid ClusterRoleBindings that grant access to CDE resources. This supports PCI DSS Req 7.2.5 by enforcing least privilege within the cluster. See: https://docs.aws.amazon.com/eks/latest/best-practices/identity-and-access-management.html |
| NS3 | No overly permissive ClusterRoleBindings | Cluster | `kubectl get clusterrolebindings -o json` | No ClusterRoleBindings grant `cluster-admin` or wildcard permissions to non-system service accounts or user groups | High | 7.2.5 | Remove or restrict ClusterRoleBindings that grant broad cluster-admin access. Use audit2rbac to generate minimal RBAC from audit logs. This supports PCI DSS Req 7.2.5 by preventing excessive privileges. See: https://docs.aws.amazon.com/eks/latest/best-practices/identity-and-access-management.html |
| NS4 | Resource quotas on CDE namespaces | CDE-only | `kubectl get resourcequotas -n {cde}` | ResourceQuotas are defined on CDE namespaces to prevent resource exhaustion and ensure payment workloads have guaranteed capacity | Medium | 2.2.1 | Apply ResourceQuotas to CDE namespaces (CPU, memory, pod count limits). This supports PCI DSS Req 2.2.1 by ensuring CDE workloads have guaranteed resources and preventing denial-of-service from resource exhaustion. See: https://kubernetes.io/docs/concepts/policy/resource-quotas/ |
| NS5 | LimitRanges on CDE namespaces | CDE-only | `kubectl get limitranges -n {cde}` | LimitRanges are defined on CDE namespaces to enforce per-pod/container resource constraints | Medium | 2.2.1 | Apply LimitRanges to CDE namespaces to set default and maximum CPU/memory per container. This prevents individual containers from consuming unbounded resources and supports PCI DSS Req 2.2.1. See: https://kubernetes.io/docs/concepts/policy/limit-range/ |
| NS6 | No shared service accounts across CDE boundary | CDE-only | `kubectl get serviceaccounts -A -o json` | CDE namespaces do not reference service accounts from non-CDE namespaces; workloads in CDE use dedicated service accounts (not `default`) | High | 7.2.5 | Create dedicated service accounts per workload in CDE namespaces. Never use the `default` service account for CDE workloads. Do not share service accounts across namespace boundaries. This supports PCI DSS Req 7.2.5 by restricting cross-boundary access. See: https://docs.aws.amazon.com/eks/latest/best-practices/identity-and-access-management.html |
| NS7 | CDE namespace labels present | CDE-only | `kubectl get namespace {cde} -o json` | CDE namespaces have labels indicating PCI scope (e.g., `pci-scope=cde` or `compliance/pci-dss=in-scope`) for auditability and policy targeting | Low | 1.4.1 | Label CDE namespaces with `pci-scope: cde` to enable policy enforcement, auditing, and automated CDE detection. This supports PCI DSS Req 1.4.1 by clearly delineating the CDE boundary. |
| NS8 | Policy enforcement engine deployed | Cluster | `kubectl get pods -A` (check for Gatekeeper, Kyverno, or Kubewarden pods) | A Kubernetes policy enforcement engine (OPA Gatekeeper, Kyverno, or Kubewarden) is deployed and operational in the cluster | High | 2.2.6 | Deploy a policy enforcement engine (Gatekeeper, Kyverno, or Kubewarden) to enforce and audit namespace-level and pod-level policies programmatically. This supports PCI DSS Req 2.2.6 by providing automated enforcement of security policies. See: https://docs.aws.amazon.com/eks/latest/best-practices/policy-management.html |
| NS9 | Default service account token automounting disabled in CDE | CDE-only | `kubectl get serviceaccounts -n {cde} -o json` + pod specs (`automountServiceAccountToken`) | The `default` service account in CDE namespaces sets `automountServiceAccountToken: false`, and CDE pods do not auto-mount tokens unless they explicitly need API access | Medium | 7.2.5 | Set `automountServiceAccountToken: false` on the `default` service account in CDE namespaces and on pods that do not call the Kubernetes API. This prevents unnecessary API credentials from being mounted into CDE workloads. Supports PCI DSS Req 7.2.5 (least privilege). See: https://kubernetes.io/docs/tasks/configure-pod-container/configure-service-account/ |
